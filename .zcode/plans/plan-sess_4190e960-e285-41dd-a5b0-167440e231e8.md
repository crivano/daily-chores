# Plano: Controle de 6 estados + edição de hora + navegação por dias + cache localStorage

## Resumo das decisões (confirmadas com você)
- **Controle único rotativo**: cada toque avança o estado na ordem **não feito → feito → cancelado → feliz → indiferente → triste → não feito...** (sem popup). Tocar em qualquer lugar da linha avança o estado.
- **Semântica**: `FEITO`, `FELIZ`, `INDIFERENTE` e `TRISTE` são "conclusivos" (param o alarme, contam no progresso, deslocam tarefas encadeadas). `CANCELADO` apenas silencia o alarme — não conta no progresso e **não** desloca cadeias (dependentes usam horário nominal).
- **Hora de conclusão**: quando existe registro, a linha mostra um pill com a hora (`completedAt` no fuso do usuário) com ícone de lápis; tocar abre um editor inline `<input type="time">` com confirmar/cancelar.
- **Navegação por dias**: setas ◀ ▶ no cabeçalho (▶ desabilita em "hoje"), data via `?d=YYYY-MM-DD`, botão "Hoje" quando visualizando dia anterior. Sem dias futuros.
- **Cache localStorage**: a página deixa de bloquear a renderização em 3 consultas sequenciais ao Neon. O shell renderiza imediatamente, os dados do dia vêm de `GET /api/day` e ficam cacheados por data no localStorage (stale-while-revalidate) — segunda visita pinta instantâneo.

## 1. Modelo de dados

**`prisma/schema.prisma`** — adicionar coluna em `Completion`:
```prisma
status String @default("DONE") // "DONE" | "CANCELLED" | "HAPPY" | "INDIFFERENT" | "SAD" (ausência = não feito)
```
- Migration `add_completion_status` (`ALTER TABLE "Completion" ADD COLUMN "status" TEXT NOT NULL DEFAULT 'DONE'`), aplicada conforme convenção do repo (DIRECT_URL), seguindo a skill **prisma-cli**; depois `prisma generate` (client em `src/generated/prisma`).
- `completedAt` continua sendo o instante do registro (regra das cadeias) e passa a ser editável.

## 2. Domínio (puro, isomórfico)

- **Novo `src/lib/domain/states.ts`**: tipo `TaskState`; `STATE_CYCLE = ["NONE","DONE","CANCELLED","HAPPY","INDIFFERENT","SA D"]`; metadados por estado (rótulo pt-BR, ícone, `conclusive: boolean`); `nextState()` e `isConclusive()`.
- **`src/lib/domain/schedule.ts`**: `shiftOf`/`effectiveAt` passam a considerar o `completedAt` da âncora **somente se conclusivo**; âncora `CANCELLED` (ou sem registro) → dependentes no horário nominal/offset.
- **Novo `src/lib/domain/day.ts`** (só tipos/DTOs, importável pelo client): `DayPayload { date, timezone, tzDefaulted, today, dateLabel, total, concluded, tasks: { timed, timeless }, alarms }` e `DayTaskDTO { taskId, name, state, completedAt: string|null, timeLabel?, shiftLabel?, note? }`.
- Supressão de alarme continua sendo "existe linha de Completion" (todo estado não-NONE suprime: conclusivos concluem, cancelado silencia) — `sync.ts` e `api/internal/alarm` só precisam de revisão/ajuste de comentários, sem mudança de comportamento, exceto o uso conclusivo nos horários efetivos.

## 3. Backend

- **Novo `src/lib/day.ts`** (server-only): extrai de `page.tsx` a função `getDayPayload(userId, d?)` — valida `d` (formato, não-futuro; ausente = hoje no fuso do usuário) e devolve o `DayPayload` completo, com `alarms` apenas quando `d === hoje`.
- **Novo `GET /api/day?d=YYYY-MM-DD`**: `auth()` → `getDayPayload` → JSON.
- **`POST /api/completions`** — novo corpo `{ taskId, date?, status: TaskState, time?: "HH:mm" }`:
  - `status: "NONE"` → deleta a linha (equivale ao `done:false` atual);
  - senão upsert: `completedAt = time ? fromZonedTime(\`${localDate}T${time}:00\`, tz) : (existente ?? new Date())` — mudar só o estado preserva a hora; novo registro sem `time` usa "agora";
  - `syncAlarms(taskId)` apenas quando `localDate === hoje` (edição de dia passado não mexe em alarmes futuros);
  - resposta: `{ ok, day: DayPayload }` do `localDate` (payload completo já resolve os shifts em cadeia de outras tarefas);
  - compat: manter mapeamento legado `done:true → DONE` / `done:false → NONE`.
- **`src/components/AlarmOverlay.tsx`**: passa a enviar `{ taskId, status: "DONE" }`.

## 4. Frontend

- **`src/app/(app)/page.tsx`** vira shell fino: `auth()` → `<DayBoard userId={userId} />` (sem Prisma, sem `force-dynamic`). Removo `TaskCheckbox` e o cálculo que migra para `lib/day.ts`.
- **Novo `src/components/DayBoard.tsx`** (client):
  - data atual via `?d=` (`useSearchParams`), navegação com `router.replace`;
  - hook de dados com **stale-while-revalidate**: ao montar/trocar de dia lê `localStorage` (`dc:day:v1:{userId}`, mapa `{ [D]: DayPayload }` com poda das ~30 datas mais recentes) e pinta imediatamente; busca `/api/day` em paralelo e atualiza estado + cache. Gate de `mounted` para evitar mismatch de hidratação (esqueleto por 1 frame na primeira ida ao cliente);
  - mutações otimistas (trocar estado, editar hora) → POST → substitui pelo `day` da resposta e grava cache; em erro, rollback + pill "Não foi possível salvar" (padrão atual);
  - cabeçalho com navegação de datas (◀ label ▶ + chip "Hoje"), aviso de fuso padrão, progresso (`concluded/total`), listas timed/timeless, estado vazio;
  - renderiza `<AlarmListener>` só no dia de hoje, com `alarms` do payload e novo prop `onTick` (refetch a cada 30s substitui `router.refresh()`; cobre virada de dia);
  - polling/dados só do dia selecionado; dias passados sem polling.
- **Novo `src/components/TaskRow.tsx`** (substitui `TaskCheckbox.tsx`):
  - linha inteira clicável → `nextState()`; ícone/estado à esquerda (círculo vazio; ✓ indigo; ⊘ cinza; 😊 😐 😟), `line-through`+dimming para conclusivos, estilo próprio para cancelado;
  - pills à direita preservados (shift, hora efetiva) + **pill de hora de conclusão** (`HH:mm ✎`, formatada com `formatInTimeZone` + `payload.timezone`) quando `completedAt ≠ null`; tocar abre editor inline `input type="time"` + ✓/✕ (botão dedicado, `stopPropagation`);
  - `aria-label`/`title` anunciando o estado atual e o próximo.
- **`src/components/AlarmListener.tsx`**: recebe `onTick?` para o intervalo de 30s (fallback `router.refresh()`).
- **`ProgressRing`**: sem mudança (recebe `concluded/total`).
